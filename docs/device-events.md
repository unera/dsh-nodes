# Что устройство присылает хосту

Единственный справочник по сообщениям, которые **инициирует само устройство**.
Всё остальное — команды хоста, они описаны в `README.md` и в объявлениях API.

Общее для всех: авторизация — токен узла (`authorization: Bearer …`), идентичность
устройства берётся из токена, а не из тела. Неизвестный `type` → `400 bad_type`,
Неизвестный тип — отказ, а не догадка.

## 1. `type: "command"` — «команда выполнена»

Не событие, а ответ на выданную команду: `POST /v1/commands/{seq}/result`.

```
POST /v1/commands/42/result
{"status":"ok","payload":{…}}          // или {"status":"error","code":"…","message":"…"}
```

`seq` — номер выданной команды, он же билет: без него ответ не примут. Команды с
`status: "pending"` (долгие: `record`, `say`, `dialog.ask`) отвечают дважды —
сначала `pending` из цикла, потом итогом из своего потока.

## 2. `type: "voice"` — устройство отдаёт звук

Живёт только на маршруте загрузки: в событиях `voice` не встречается, поэтому и
`action` не нужен — тип однозначно называет маршрут.

```
POST /v1/upload-file?type=voice&filetype=wav&id=<id>&synth=device|host
authorization: Bearer …
content-length: <байты>
content-type: audio/wav
x-seconds: 1.9
x-record-start: 1794604817640   // epoch ms, необязательные
x-record-stop:  1794604820436
x-sent-at:      1794604820439
<тело: байты файла>
```

- `filetype` обязателен: `wav`, `ogg`, `opus`, `mp3`, `m4a`, `flac`;
- `id` — идентификатор нажатия (дедупликация), `[A-Za-z0-9_-]`, до 64 знаков;
- `synth` — `device` (по умолчанию) или `host`;
- путь выбирает **сервер**: `$DSH_HOME/cache/voice/incoming/<id>.<filetype>`;
- ответ `202 {"accepted":true,"id":…,"path":…,"bytes":…,"seconds":…}`;
- после записи хост эмитит `dsh-nodes/voice` и дальше всё делает плагин голоса.

## 3. `type: "new-session"` — начать новый разговор

```
POST /v1/events   {"type":"new-session"}
→ 202 {"accepted":true,"device":"…"}
```

Текста и сессии не требуется. Хост забывает, с какой сессией говорило это
устройство; следующий ввод создаёт новую. Если в этот момент идёт обмен — сброс
применяется после его завершения, чтобы уже сказанная фраза не потерялась.

## 4. `type: "notify-button"` — нажали кнопку в шторке

```
POST /v1/events
{"type":"notify-button","notification":"<id>","button":"b2","id":"<нажатие>"}
→ 200 {"delivered":true,"session":"…"}
→ 200 {"delivered":false,"already":true}      // кнопку уже нажимали
```

Смысл восстанавливает **сервер** по своей записи уведомления: подпись кнопки,
`purpose` и сессию берёт из БД, а не из тела. Устройство не говорит за человека.

## 5. `type: "notify-session"` — текст из шторки прямо в сессию

```
POST /v1/events
{"type":"notify-session","session":"session-…","text":"…","purpose":"…"}
→ 200 {"delivered":true,"session":"…"}
```

Быстрый ввод без голоса: текст попадает в указанную сессию как сообщение с
устройства. `purpose` — необязательная пометка «зачем», её пишет хост.

## 6. `type: "form"` — форма (задел)

Отвечает `501 form_not_supported`. Появится вместе с приёмом форм.

## Совместимость

Старый `type: "notify"` и события без `type` продолжают работать: если в теле есть
`notification` — это `notify-button`, иначе `notify-session`. Хост один раз пишет
в журнал, что тип пришлось угадать.

## Как добавить новый тип

1. добавить значение в `eventTypeOf` (`dsh-nodes/lib/voice-upload.mjs` рядом с
   остальными) и в этот файл — одной строкой в оглавление выше;
2. решить, что происходит: доставка в сессию, эмит события для плагина, или отказ;
3. тест на приём и на отказ (`bad_type`);
4. если тип инициирует что-то в предметной области (как `voice`), слушать его
   должен плагин, а не узлы: узлы только принимают и эмитят.
