# dsh-nodes — план

Статус: обсуждается, кода нет.
Дата: 2026-11-05.
Пакет: `@dr-co/dsh-nodes`, репозиторий `unera/dsh-nodes`, BASE = `/dsh-nodes`.

Старый `dsh-node` (push-модель, 2026-10-21) дропнут: вынесен из `src/` в
`backups/dsh-node-dropped-20261105/`, в проекте не используется.

## 1. Идея и главное ограничение

DSH — **узлы** (машины и устройства) объявляют, какие **API** они реализуют;
на сервере есть **справочник API** — контракты с методами и схемами; модель
смотрит справочник и зовёт `nodes_call(node, api_no, method, data, timeout)`.

Ограничение, из-за которого так: **схемы тулов едят контекст модели**.
Если каждый узел публикует свои тулы, то десять узлов с одинаковым `shell`
дают десять схем на один и тот же `exec` — и это ещё до того, как модель
прочитает хоть строчку задачи. Справочник платит один раз: четыре тула
постоянно, независимо от числа узлов и методов.

```
        DSH (сервер)                                   узлы
  ┌────────────────────────┐                  ┌──────────────────────┐
  │ ctx.tools              │  WS  /v1/ws      │ nbw                  │
  │  nodes_catalog         │ ◀──────────────▶ │  client dsh-nodes    │
  │  nodes_api             │                  │  MCP: fs, git, shell │
  │  nodes_list            │  HTTP /commands  ├──────────────────────┤
  │  nodes_call            │ ◀──────────────▶ │ лампа в комнате      │
  │                        │  PUT /announce   │  свой код, api=lamp  │
  │ справочник + реестр    │ ◀─────────────── │                      │
  │ очередь + промисы      │                  └──────────────────────┘
  └────────────────────────┘
```

Роли асимметричны: **сервер инициирует вызовы**, узел отвечает и объявляет,
что умеет. Узел не может позвать сервер ничем, кроме `PUT /announce`,
`GET /commands`, `POST /result`.

## 2. Справочник API

Единица справочника — запись API:

| поле | смысл |
|---|---|
| `id` | короткий номер, который видит и называет модель: `1`, `2`, `3`; выдаёт сервер, номера не переиспользуются |
| `key` | по чему матчатся объявления: хеш от `(name, version)`, а если версии нет — от `(name, nodeId)` |
| `name` | человеческое имя из узла, свободный текст: `linux shell` |
| `version` | версия контракта из узла: `1.14.11`; нет версии — API личное для этого узла |
| `refcount` | сколько узлов держат API: `COUNT(*)` по `node_api`, не хранится |
| `nodes` | узлы, объявившие API: строки таблицы `node_api` |
| `apidef` | контракт: описание и методы с JSON Schema аргументов |

Запись появляется **только из объявления узла** — руками её не заводят, чтобы
справочник не врал о том, что реально существует. Руками можно поправить
`apidef`, но запись живёт ровно столько, сколько её держит хоть один узел:
«пришпиленных» записей нет (решение: не нужны). Правка схемы, которая должна
пережить уход узлов, делается в источнике — на узле.

Три разных понятия, которые нельзя путать:

- **`name`** — то, как API зовут люди (`linux shell`). Пробелы, регистр, что
  угодно; в вызовах не участвует.
- **`key`** — тождество контракта. `linux shell` + `1.14.11` на пяти машинах —
  один `key`, одна запись, `refcount: 5`. Без версии тождество включает узел:
  две ноды, объявившие `linux shell` без версии, — две разные записи, потому
  что поручиться за совместимость их контрактов нечем.
- **`id`** — короткое имя для модели. Отдельное от `key`, потому что
  `linux shell@1.14.11` в каждом вызове — это токены и опечатки, а номер
  копируется без ошибок.

**Модель видит только `id` и `name`.** `key` и `version` — служебные: раз они
не участвуют в вызове, показывать их незачем, модель на них и не смотрит.
Версия появляется в каталоге в одном случае — когда две записи называются
одинаково и их надо различить (`3 — linux shell (1.14.11)`,
`7 — linux shell (2.0)`); в остальных её видно только в админке.

```yaml
id: 3
key: sha256("linux shell" + version "1.14.11")     # внутреннее, модель не видит
name: linux shell
version: 1.14.11
description: Shell на машине узла
methods:
  exec:
    args: {command: {type: string}, cwd: {type: string}}
    description: Выполнить команду
  list: {args: {}, description: Что уже запущено}
nodes: [nbw, desktop, vps]
refcount: 3
```

### 2.1. Приход: объявление — это множество, не счётчик

`PUT /announce` приносит **полный список** того, что узел реализует:

```json
{"proto": 1, "client_version": "dsh-nodes/0.1.0",
 "apis": [{"name": "linux shell", "version": "1.14.11", "methods": [...]},
          {"name": "fs", "methods": [...]}]}
```

Сервер считает `key` для каждой: `(name, version)`, либо `(name, nodeId)`, если
версии нет. Дальше — операция над множествами:

```
old = node.apis                     # номера, которые узел держал до объявления
new = номера записей: для каждого key — существующая или только что созданная
added   = new \ old     # insert в node_api (refcount вырастет сам: это COUNT)
removed = old \ new     # delete из node_api
node.apis = new
```

Сканировать справочник не нужно: номера, которые узел держит, лежат в
`node_api`, поэтому разность считается по двум маленьким спискам. Все правки
(`node_api`, `api`) идут одной транзакцией (§11).

`name` — свободный текст, сервер его не валидирует и не парсит: `linux shell`
с пробелом — нормальное имя. В вызовах участвует не оно, а `id`.

Если узел прислал методы **вообще без имени**, сервер подставляет
`name = "node <id>"` — номер узла постоянен, значит и имя, и `key` постоянны.
Хранить для этого нечего (`auto_api` не нужен), а справочник не дрожит на
каждом коннекте.

Номера `id` выдаёт `INTEGER PRIMARY KEY AUTOINCREMENT` (§11), они не
переиспользуются. Удалённая запись оставляет дырку навсегда — иначе номер из
прошлой сессии мог бы указать на другой API.

Порядок из «сначала инкремент, потом обход старых записей с декрементом»
опасен: если декрементить все записи узла без исключения только что
добавленных, у стабильного API получится `+1 -1` и он сам себя удалит.
Поэтому считаем **разность множеств**, а не пару инкремент/декремент —
порядок перестаёт иметь значение, а ошибка становится невозможной.

### 2.2. Уход: связи и уборка

- Связь `node_api` исчезает только по двум поводам: узел объявил новый
  список без этого API, либо узел удалён из админки (`ON DELETE CASCADE`).
- Офлайн — не повод: узел, который отвалился, продолжает держать свои записи,
  иначе справочник (и типизированные тулы) дрожал бы на каждом реконнекте.
- `refcount` — это `COUNT(*)` по `node_api`, а не хранимое поле (§11): одна
  правда, а не денормализация, которую надо не забыть обновить.
- Связей не осталось → запись удаляется вместе со схемой. Так версии API
  (`lamp`, `lamp2`) не копятся: как только последний узел перестал объявлять
  старую, она исчезает.
- Правка `apidef` руками живёт, пока живёт запись. Если схема должна пережить
  уход всех узлов — её правят в источнике, на узле.
- Санитарная проверка на старте: `api` без связей в `node_api` удаляются,
  `node_alias` без узлов не остаётся благодаря каскаду. Проверка дешёвая и
  ловит следы падения посреди транзакции.

### 2.3. Схемы и расхождения

- `apidef` ставится при создании записи; следующие объявления только
  сравниваются с ним.
- Расхождение (узел принёс метод с другой схемой или другой набор методов) —
  предупреждение в админке и в лог. Справочник не перезаписывается молча:
  иначе схема, которую видит модель, зависела бы от порядка коннектов.
- Вызов всё равно уходит: если узел реализует контракт иначе, модель получит
  `bad args` от сервера (§5.2) или ошибку от узла. Пользователь разбирается.
- В админке у записи есть кнопка «принять схему от узла X» — осознанный выбор
  вместо тихой замены.
- Метод **обязан** иметь `args` в `apidef`, хотя бы пустой объект. Нет схемы —
  публикация отклоняется: иначе валидация молча пропускала бы всё, и «bad args»
  работал бы через раз.
- **`apidef` — недоверенный вход.** Это JSON Schema от узла, которую исполняет
  наш валидатор, поэтому на `/announce` она проверяется до сохранения:
  - диалект только 2020-12, `strict` (неизвестные ключи — ошибка, не
    игнорируются);
  - `$ref` разрешены только локальные (`#/...`); `$id` и любые внешние URL
    запрещены — иначе узел заставит сервер сходить по своей ссылке (SSRF);
  - потолки: 64 КиБ на `apidef` одного API, глубина 32, число ключей схемы 4096;
  - схема компилируется `ajv.compile` при объявлении; не скомпилировалась —
    публикация отклоняется с `bad_request` и текстом ошибки.
  Это дешевле, чем кажется, и убирает класс атак, которого в первой версии
  плана не было вовсе.

## 3. Узел

На диске (§11.2):

```
node        { id, local, name, token_sha256, token_issued_at, proto, client_version,
              created_at, last_seen }
node_alias  { alias, node }
node_api    { node, api }          -- apis[] собирается из этой таблицы
```

В памяти, на текущую жизнь процесса (§11.4): `state`, `served`, `waiting`,
`online`, `queue`. Они не персистятся — поколение сервера различает `epoch`.

- `id` — автоинкрементный **номер** (`17`), он же адрес узла в вызовах.
  Отдельного uuid нет: один идентификатор вместо двух, и номер не
  переиспользуется (тот же `AUTOINCREMENT`, что у API).
- `name` — основное имя для человека, его печатает админка и `nodes_list`.
- `aliases[]` — все имена, которыми узел можно позвать: `name` плюс добавленные
  в админке (`nbw`, `ноутбук`, `lamp-kitchen`). Свободный текст, кириллица
  допустима. Уникальность проверяется по **всем** алиасам всех узлов.
- `proto` — версия нашего протокола, которую назвал узел. **Только факт, не
  гейт:** старая версия никуда не отказывается. По ней в админке и в логе
  видно, кто с чем пришёл, и больше ничего.
- `client_version` — чем узел себя назвал: `dsh-nodes/0.1.0`, `lampd 2.1`.
  Только для админки и логов, никакой логики на нём не построено.
- `served` (в памяти) — watermark сервера: до какого номера он уже выдал этому
  узлу работу. Поднимается выдачей пачки до `max(seq)`, только вверх и только
  в пределах поколения. Курсор узла (поле `known` в кадрах `hello`/`alive`) —
  отдельная величина:
  сервер её слушает, но не путает со своей.
- `apis[]` — номера API, которые узел держит прямо сейчас: строки `node_api`.
  Отдельного поля нет, поэтому и согласовывать нечего.

Создаётся в админке: имя + токен. Объявляет себя через `PUT /announce` списком
`apis` (имя, версия, методы) и версией клиента. Узел не публикует имена тулов
для модели — только что умеет.

Онлайн/офлайн — по WS (§7). Офлайн-узел остаётся в справочнике и в списке
узлов, и вызов к нему всё равно принимается: команда ждёт в очереди до своего
`timeout`. Быстрого отказа «узел не на связи» нет — узел может вернуться без
рестарта и всё исполнить, а гадать, вернётся ли, мы не будем.

**Версии не гейтят, возможности объявляются.** Узел присылает `proto` и набор
возможностей (`sandbox`, `allow_escalation`). Сервер не сверяет версию с
минимумом — он смотрит на возможности:

- нет `sandbox` в объявлении → `access = none`: узел **не умеет** изолировать,
  и это не то же самое, что «умеет всё». Поэтому любой вызов из сессии с
  ограничениями получает `sandbox_denied` (`node cannot confine`), а обёртка
  сразу предлагает эскалацию (§13.3). Вызов из сессии в `danger-full-access`
  проходит без вопросов: там изоляции и не требуется;
- нет `allow_escalation` → эскалация к этому узлу невозможна, вызов сразу
  отвечает `escalation unsupported`;
- незнакомый кадр или неразбираемый JSON → закрытие с кодом `4400` и внятной
  причиной. Это отказ **парсера**, а не проверка версии.

Старый клиент уходит, новый приходит, откатились на старый — ничего
страшного: пока кадры разбираются, сервер работает. Ломается только то, что
ломается по факту, а не по номеру версии.

Устройство, которое не тянет WebSocket и JSON, — это отдельный узел-бридж на
хосте (Zigbee/Modbus/MQTT), объявляющий API `lamp` один раз. Отдельного
«device»-слоя в протоколе нет и не планируется: адресация устройства — поле
внутри аргументов метода (`device: enum[lamp1, lamp2]`), то есть дело
контракта, а не транспорта.

## 4. Транспорт до узла

- **WS `/dsh-nodes/v1/ws`** — события сервер→узел («есть работа», изменение
  справочника) и presence (`alive` раз в 20–30 с).
- **HTTP** — `PUT /announce`, `GET /catalog`, `GET /commands`, `POST /result`,
  `GET /state`.

Почему не всё по WS: команда по HTTP — отдельный запрос, потеря соединения
посреди вызова ничего не рвёт, отладка через `curl`, узел может быть скриптом
на пять строк.

### 4.1. Номера команд и state узла

У каждой команды — номер из **счётчика узла**: `state[node]` растёт на 1 при
каждой постановке. Это и есть то самое «постоянно растущее число»: один
монотонный счётчик на узел.

`state` живёт **в памяти** и обнуляется при старте сервера вместе со списком
команд (§4.7). Поэтому номер `17` значит «семнадцатая команда этого узла в
текущей жизни сервера», а не «за всё время»: за это платит epoch, а не
персистентность счётчика.

```
постановка команды  → state[node] += 1, команда получает этот номер
узел знает свой курсор (последний обработанный номер)
```

`state` — не «сколько в очереди», а «номер последней поставленной работы».
Узел по нему понимает, стоит ли идти за пачкой, а сервер — отстал ли узел.

**Разница `state - cursor` — не количество работы.** Команды могут истечь
(`timeout`, `commandTtl`), не дойдя до узла, и тогда номер есть, а команды
нет. Поэтому `state` годится только как повод проснуться, а точный ответ даёт
запрос: пустой ответ значит «по этому курсору больше ничего», и только он
останавливает цикл (§4.3).

### 4.2. Подписка: как узел узнаёт, что есть работа

WS несёт **только число**. Команды по-прежнему едут по HTTP.

**Рукопожатие.** Токен уже проверен по заголовку, поэтому первым кадром идёт
не аутентификация, а сверка поколений:

```
узел → сервер  {"t":"hello","epoch":12,"boot":"a3f1…","known":188,"proto":1}
сервер → узел  {"t":"hello-ok","epoch":19,"boot":"7c02…","state":0}
```

Правила рукопожатия:

- токен проверяется заголовком до upgrade; кадр `hello` — про поколение, не про
  аутентификацию;
- `hello` не пришёл за `helloTimeoutSeconds` (по умолчанию 10) → закрытие
  `4400`, узел в presence не попадает;
- `hello` не по схеме (нет `epoch`, мусор вместо JSON) → закрытие `4400` с
  причиной; это отказ парсера, а не проверка версии (§3);
- повторный `hello` на том же сокете → идемпотентный `hello-ok`, без
  переинициализации и без второго «коннекта»; узел после этого считается
  online, `waiting` = false;
- пока `hello-ok` не отправлен, сервер не шлёт `state`: узлу ещё нечего
  сверять, и кадр ушёл бы в никуда.

`known: null` — узел перезапустился (§4.6). Несовпадение `epoch`/`boot` —
**это и есть реконнект**: сервер в ответе называет своё поколение, узел
обнуляет курсор (`cursor := 0`), и дальше всё как при `null`, только без
поиска «незакрытого хвоста» — его физически нет, очередь умерла с процессом
(§4.7).

Почему на рукопожатии, а не в ответах: рестарт сервера убивает сокеты, значит
каждый узел переподключится сам и принесёт свой `epoch`. Простаивающий узел
не остаётся в неведении — молчание сервера в ветке «делать нечего» перестаёт
быть дырой, потому что поколение сверяется при соединении, а не при работе.

Узел, периодически (`alive`, раз в 20–30 с):

```json
{"t": "alive", "known": 27, "epoch": 12, "boot": "a3f1…"}
```

Сервер держит на узел два факта: `state` и флаг `waiting` («узел спрашивал и
ждёт ответа»).

```
получен alive(known):
    если known = null → особый путь, §4.6
    иначе если state > served → сразу шлём {"t":"state","state":31,"epoch":12,"boot":"a3f1…"}
    иначе                    → waiting = true     # ответить пока нечего

state изменился:
    если waiting      → шлём {"t":"state","state":N,"epoch":…,"boot":…}; waiting = false
    иначе             → ничего не делаем
```

Свойства, ради которых так:

- **Схлопывание.** Сервер шлёт максимум один `state` на один вопрос узла,
  даже если между вопросами state вырос на десять. Очередь уведомлений не
  копится в принципе: слать нечего, кроме текущего числа.
- **Back-pressure бесплатно.** Частота сообщений задаётся частотой `alive`, а
  её выбирает узел — тот, кто знает, успевает ли он исполнять. Медленное
  устройство не получает град сообщений, быстрому никто не мешает.
Предикат «есть работа» один на весь документ: `state > served`. Не `state >
known` — курсор узла это его заявление о себе, а `served` — факт сервера; если
сравнивать с чужим числом, работа может спрятаться (узел заявил курсор впереди
`served`, сервер поверил и замолчал).

- **Потеря сообщения ничего не стоит.** Следующий `alive` с тем же `known`
  снова увидит `state > served` и получит ответ. Догоняющая доставка — не
  отдельный механизм, а следствие сравнения чисел.
- **Порядок не нужен.** Достаточно `>`/`!=`: важно лишь, что узел не знает
  последнего номера.

Получив `state`, узел делает `GET /commands?after=<known>&limit=5`, исполняет
и повторяет — пока ответ не окажется пустым. Пустой ответ и есть «всё».

### 4.3. Выдача команд: строго после курсора

```json
GET /dsh-nodes/v1/commands?after=16&limit=5
{"state": 88, "epoch": 12, "boot": "a3f1…",
 "commands": [
   {"seq": 17, "api": 2, "method": "file-ls", "args": {"path": "/"}, "timeout": 120,
    "sandbox": {"mode": "read-only", "root": "/home/u/work"}},
   {"seq": 18, "api": 2, "method": "file-ls", "args": {"path": "/tmp"}, "timeout": 120,
    "sandbox": {"mode": "workspace-write", "root": "/home/u/work"},
    "approved": {"denial_id": "d-7f3", "mode": "workspace-write"}}]}
```

Это **единственная** форма команды: здесь и только здесь она описана, §13.2
на неё ссылается. Поля:

| поле | обязательное | смысл |
|---|---|---|
| `seq` | да | номер команды у этого узла |
| `api`, `method`, `args` | да | что исполнять; `args` валидируются по `apidef` |
| `timeout` | да | секунды; вызов → узел → конфиг (60) |
| `sandbox` | да | `{mode, root}` из сессии модели; для `danger-full-access` → `{"mode":"danger-full-access"}` |
| `approved` | нет | `{denial_id, mode}` — обход после аппрува (§13.3) |

Цикл узла:

```
1. курсор = 188 (узел помнит его сам; при первом запуске — null)
2. сервер сказал state = 201 → 201 > 188, стоит сходить
3. GET /commands?after=188&limit=5 → 189, 190, 191
4. исполнил, закрыл → курсор = 191
5. сразу снова: ?after=191&limit=5 → 192, 193
6. курсор = 193, снова → пустой ответ
7. пустой ответ = «по этому курсору больше ничего» → курсор := state (201),
   спим до следующего alive
```

**Условие остановки — пустой ответ, а не сравнение чисел.** «Курсор догнал
`state`» кажется эквивалентным, но врёт: если команды `194…201` истекли по
`commandTtl` или таймауту, не дойдя до узла, номера остались, а команд нет —
и узел, сравнивающий числа, спрашивал бы вечно. Пустой ответ такого не
допускает: сервер прямо сказал «нечего», и это единственный факт, на который
опирается цикл. Заодно это развязывает руки нумерации в будущем: дырки в
номерах перестают быть проблемой клиента.

- **Никаких `7` после `16`.** Номер команды монотонен в пределах узла, выдача
  фильтруется по `after` строго. То, что узел взял раньше, он уже взял;
  повторно сервер это не предлагает.
- **Два разных числа, и их нельзя путать:**
  - `cursor` — курсор **узла**: последний номер, который он закрыл. Живёт на
    узле, приходит в `hello`/`alive` (`known`), сервер его только слушает.
  - `served` — watermark **сервера**: последний номер, который он выдал этому
    узлу. Поднимается выдачей пачки (`served = max(served, max(seq) пачки)`).
  Имя `known` осталось только у кадра, чтобы не плодить переименования;
  внутри сервера это `served`, и в §11.4 так и записано.
- `served` монотонен **в пределах поколения**: только вверх, до рестарта узла
  (§4.6 обнуляет его вместе с очередью — это не понижение, а новое поколение
  узла) и до рестарта сервера (§4.7). Узел, сообщивший `cursor` меньше
  `served`, потерял курсор без `null` — предупреждение в лог и админку, но
  само число не откатывается.
- Команда уходит из очереди, когда пришёл результат, истёк `timeout`, вышел
  `commandTtl` или узел отказал (`sandbox_denied`, команда не запускалась).
- Курсор двигает узел: после закрытия пачки — на `max(seq)`; при пустом
  ответе, когда `state` впереди, — на `state`.
- Пачка маленькая (5) намеренно: одно устройство не забирает полсотни команд
  и не растягивает свой ход на минуты.
- Доставка — **at-most-once**. Повтора нет даже при рестарте узла: хвост
  `seq <= served` отменяется ошибкой (§4.6), а не переотдаётся. Поэтому клиенту
  не нужен дедуп по `seq` — только разумные таймауты.

**Судьба команды — одна таблица, без «и ушла, и осталась».** Раньше в двух
соседних абзацах было написано и то, и другое; правильный ответ:

| событие | в очереди | ждущий промис | поздний `POST /result` |
|---|---|---|---|
| пришёл результат | удаляется сразу | резолвится | `409` (уже закрыта) |
| истёк `timeout` вызова | **удаляется сразу** | резолвится в `timeout` | `409` |
| узел отдал `sandbox_denied` | удаляется сразу | резолвится в ошибку | `409` |
| истёк `commandTtl` | удаляется | уже закрыт таймаутом | `404` (номера больше нет) |
| узел прислал `known: null` и `seq <= served` | удаляется | резолвится в `Node was restarted` | `409` |
| рестарт сервера | очереди нет | процесса нет | `404` |

То есть команда **не живёт в очереди после таймаута**: `commandTtl`
существует только для команд, которые ещё ни разу не выдавались (узел не
забрал), и на закрытые не действует. Слова «остаётся до `commandTtl`, но уже
никогда не будет выдана» вычеркнуты как противоречивые.

### 4.4. Команда = промис

```js
const { status, message, results } = await enqueue(nodeId, apiNo, method, args, timeoutSeconds);
```

| событие | что получает ожидающий |
|---|---|
| `result`, `ok: true` | `{status:'ok', message:null, results:[…]}` |
| `result`, `ok: false` | `{status:'error', message:'<текст>', results:null}` |
| истёк `timeout` (секунды) | `{status:'timeout', message:'Timeout reached', results:null}` |
| вызов отменён (стоп, конец хода) | команда снята из очереди, `{status:'error', message:'cancelled'}` |
| WS узла закрылось | ничего: ждём `timeout` команды; результат принимается и после реконнекта (§7) |
| узел прислал `known: null` и команда не новее его последнего курсора | `{status:'error', message:'Node was restarted', results:null}` (§4.6) |
| узел неизвестен/отозван | `{status:'error', message:'unknown node', results:null}` |
| `api`/`method` нет в справочнике | `{status:'error', message:'unknown api/method', results:null}` |
| аргументы не прошли схему | `{status:'error', message:'bad args: …', results:null}` — узел не тревожим |
| `data` больше `maxArgsBytes` | `{status:'error', message:'args too large: 48 KiB > 16 KiB'}` — узел не тревожим |
| `results` от узла больше `maxResultBytes` | `{status:'error', message:'result too large: …'}` — узел об этом узнаёт по `413` |
| очередь узла на потолке | `{status:'error', message:'queue_full: у узла 100 незакрытых команд'}` — номер `state` при этом **не расходуется** |
| тело запроса больше `maxBodyBytes` | `413`, код `body_too_large` |

Таймер снимается на любом исходе; поздний `POST /result` на закрытую команду
получает `409` и пишется в лог.

**Результаты асинхронны и неупорядочены.** Взяв пачку, узел может исполнять её
как угодно — параллельно, с разной длительностью, — и присылать `POST /result`
по каждой команде в любом порядке. Ключ — `seq`, а не позиция в очереди,
поэтому:

- медленный `file-ls` не держит быстрый `ping`: промис у каждого свой;
- несколько моделей могут звать команды на одном узле одновременно и ждать
  каждая только своё;
- результат принимается и после переподключения WS: соединение в ключе не
  участвует, `seq` живёт дольше сокета;
- таймер считается **от постановки**, а не от выдачи: модель ждёт с момента
  вызова, включая время в очереди.

### 4.4.1. Отмена вызова

Отмена — это **удаление команды из очереди**, и больше ничего. Узлу никакого
кадра не летит: остановить уже запущенный процесс на чужой машине мы не умеем
и не делаем вид, что умеем.

- команда ещё в очереди → удаляем, промис резолвится в `cancelled`, узел о ней
  никогда не узнает;
- команда уже выдана → узел доисполнит, а результат придёт «поздним» и будет
  отброшен по общему правилу (§4.5: `seq <= served` → `409`, счётчик «поздние
  результаты»). Это не ошибка, а штатный исход;
- `state` при этом не откатывается: номер израсходован, дырки в нумерации —
  норма (цикл узла всё равно останавливается по пустому ответу, §4.3).

**Отмена во время ожидания аппрува.** Промис в этот момент висит не на
команде, а на `ctx.approval.request(...)`, у которого есть свой `AbortSignal`.
При отмене вызова:

- сигнал аппрува обрывается, диалог закрывается как `cancelled`;
- на узел не уходит ничего: эскалированная команда ещё не создана;
- `denial_id` из этого отказа забывается — обёртка его просто не использует;
- модель получает `cancelled`, как и при отмене обычной команды.

Если же «да» уже получено и эскалированная команда успела встать в очередь —
её снимает обычное правило выше: удаление из очереди.

Чего сознательно нет: кадра `{"t":"cancel"}`. Он требовал бы от узла умения
прервать работу и отчёта о прерывании, а проверить это нельзя — узел может
сказать «прекратил» и продолжить. Меньше протокола, меньше лжи.

### 4.5. Возврат результата

`POST /dsh-nodes/v1/commands/{seq}/result`:

```json
{"ok": true,
 "results": [{"type": "text", "text": "on"}],
 "sandbox": {"mode": "read-only", "enforcement": "full", "denied": null}}

{"ok": false, "code": "sandbox_denied", "message": "node cannot confine",
 "denial": {"denial_id": "d-7f3", "kind": "mode",
            "requested": {"mode": "read-only"}, "granted": {"mode": "none"}}}

{"ok": false, "code": "internal", "message": "relay stuck"}
```

Тоже единственная форма: `ok`, при успехе `results` и фактический `sandbox`
(`mode`, `enforcement`, `denied` — диалект отказа, §13.2), при неудаче `code` из
словаря §17 и `message`; `denial` приходит только вместе с `sandbox_denied`.

Ответы: `200` принято, `409` — команда уже закрыта, `404` — такого номера у
этого узла не было.

Различать их можно без памяти о закрытых командах, одной арифметикой:

- `seq <= served` → номер в этом поколении существовал, значит он закрыт → `409`;
- `seq > served` → номер ещё не выдавался или его не было → `404`;
- чужой узел → `404` всегда: существование чужих номеров мы не подтверждаем.

После рестарта сервера `served = 0`, поэтому любой поздний результат даёт
`404` — ровно как в таблице §4.3.

**Поздний результат — норма, а не сбой.** Команда закрывается раньше, чем
узел успел ответить (истёк `timeout`, модели уже вернули ошибку), а результат
всё равно придёт: узел мог не успеть узнать про таймаут, или сеть подвисла.
Правила:

- `409` для закрытой команды, и `409` для узла означает «уже принято», а не
  «повтори». Ретраить `POST` бессмысленно в любом случае;
- ожидающего промиса уже нет — сервер ничего не будит и не падает;
- запись команды из очереди всё равно убирается: результат пришёл, держать её
  до `commandTtl` незачем;
- пишется строка в лог и инкрементится счётчик «поздние результаты» в админке:
  это самый честный индикатор, что узел работает медленнее, чем модель ждёт;
- после рестарта сервера такого `seq` в памяти нет вообще → `404`, и узел
  видит по `epoch`/`boot`, что разговаривает с другой жизнью сервера.

### 4.6. Рестарт узла: `known = null`

Два рестарта — два разных события, и путать их нельзя:

| что случилось | что теряется | кто страдает |
|---|---|---|
| **узел** прислал `known: null` | только хвост `≤ known` этого узла | промисы этих команд; остальные ждут дальше |
| **сервер** перезапустился (§4.7) | очередь целиком, счётчики с нуля | все ожидающие промисы (их процесс уже не существует) |

Рестарт узла **не чистит очередь узла**. Он отменяет ровно то, что узел уже
взял и не закрыл: `seq <= known`. Всё, что выше, остаётся в очереди и будет
выдано рестартнувшемуся узлу — там его и ждут.

Пример, ради которого это так:

```
очередь узла: 188, 199, 201, 202
watermark known = 200     (188 и 199 узел взял, 201 и 202 ещё нет)

узел падает и приходит с known: null

1. промисы 188 и 199 → { status:'error', message:'Node was restarted' }
2. 188, 199 убираются из очереди
3. узлу уходит текущий state (202)
4. served := 0            (узел снова ничего не брал)
итог: узел с курсором 0 забирает 201 и 202 — их промисы живы и дожидаются
```

То есть один поток получает ошибку, другой выживает. Терять всё было бы
неоправданно: 201 и 202 никто не брал, они в целости.

Почему `≤ known` отменяется, а не переотдаётся: узел эти команды брал, и
неизвестно, исполнил ли. Повторить `rm` или `systemctl restart` второй раз
хуже, чем вернуть модели `Node was restarted` и дать человеку решить. А то,
что выше watermark, — не взято, и повторять там нечего.

Про шаг 4: `served := 0`, а не `served := state`. Watermark означает «сколько
уже отдано», и после рестарта узла это снова ноль; записав туда `state`, мы бы
объявили отданным то, что ещё лежит в очереди, и сломали условие
`state > served`, по которому сервер решает «есть работа». Фрейм `state` узел
всё равно получает — шагом 3, немедленно.

Отдельно: `null` в **первом** соединении — не рестарт, а первый запуск.
`known` ещё пуст, шаг 1 ничего не отклоняет, узел начинает с 0.

### 4.7. Рестарт сервера: epoch

Узел переживает рестарт сервера — он и должен переживать, это его смысл. Но
вместе с сервером умерли и счётчики: `state` снова `0`, очередь пуста, а у
узла в памяти курсор `202`. Сравнение «`state` 0 против курсора 202» само по
себе не отвечает на вопрос: сервер отстал или это другой сервер?

`epoch` — счётчик жизней сервера. Хранится в `meta`, инкрементируется при
каждом старте.

**Старт сервера:**

```
meta.epoch += 1
state[node] := 0     для всех узлов
known[node] := NULL  для всех узлов
очередь команд := пусто
```

**Что видит узел.** `epoch` и `boot` приходят в `hello-ok` при каждом
соединении, а также в `{"t":"state"}` и в теле `GET /commands` и `GET /state` —
на случай, если соединение пережило подмену сервера (такого быть не должно, но
дешевле сверить лишний раз). Узел их запоминает и повторяет в следующем
`hello`.

**Три случая для узла:**

| что видит узел | что делает |
|---|---|
| epoch тот же, `state > served` | работа есть, обычный цикл (§4.3) |
| epoch тот же, `state <= served` | ничего, спит до следующего `alive` |
| epoch другой | сервер перезапущен: узел ставит курсор `0`, epoch := новый. Отменять нечего — очередь умерла вместе с процессом, промисов не осталось, `state` уже 0 |

Третья строка и есть ответ на «что делать с неумершими нодами»: они не
зависают и не ждут команду `203`, которую никто уже не выдаст.

**Почему не «просто персистить `state`».** Тогда бы номер означал «за всё
время», узел с курсором `202` продолжал бы после рестарта с `203`, и всё
сходилось бы без epoch. Но персистентный счётчик — это обязательство, которое
надо держать консистентным с очередью (которую мы намеренно держим в памяти),
и он не спасает от восстановления базы из бэкапа. Epoch решает ту же задачу
одним числом: «это та же жизнь сервера или другая».

**Дырка — восстановление базы из бэкапа.** Вернули `meta.epoch = 12`, а узел
помнит `12` из той же жизни и не заметит подмены: его курсор `202` снова
указывает в пустоту. Поэтому `epoch` — не только счётчик: к нему добавляется
`boot_id` (uuid, генерируется на старте, в базу не пишется, в ответах едет
рядом с epoch). Счётчик удобен для чтения глазами в админке, `boot_id` — для
сравнения, которое нельзя случайно восстановить из бэкапа.

## 5. Что видит модель

Четыре тула, постоянные, независимо от числа узлов:

| тул | зачем | стоимость |
|---|---|---|
| `nodes_catalog()` | `id — name — методы`, без версий и хешей | ~одна строка на API |
| `nodes_api(api_no)` | методы выбранного API со схемами аргументов | по запросу |
| `nodes_list()` | узлы: `алиасы — online/offline + сколько молчит — apis[]` | по запросу |
| `nodes_call(node, api_no, method, data, timeout?)` | вызов; `timeout` в секундах перекрывает узел, дефолт узла, иначе 60 | — |

Свежесть узла — **факт, который видит модель**, а не приговор сервера:

```
17 — nbw (online)            apis: 2, 5
21 — desktop (offline 3h)    apis: 3
```

`offline` не запрещает вызов: команда встанет в очередь и будет ждать своего
`timeout` (§3). Но модель теперь может поступить по-человечески — сразу
сказать «`desktop` молчит три часа, кажется, он выключен» вместо того, чтобы
запустить команду и вернуть пользователю `timeout` через двадцать секунд.
Решение принимает модель, сервер предоставляет число и не мешает.

Время считается от последнего `alive`/`hello`; в админке то же значение
показывается точной датой, в `nodes_list` — грубо (`12s`, `5m`, `3h`, `2d`),
потому что модели нужна оценка, а не секунды.

### 5.1. Сценарий «работай на узле nbw»

1. Пользователь: «далее работай на nbw, вот план».
2. Модель: `nodes_list()` → `17 — nbw (online), apis: 3 (linux shell), 4 (fs)`.
3. Модель: `nodes_catalog()` → `3 — linux shell (exec, list)`, `4 — fs (read, write)`.
4. Модель: `nodes_api(4)` → `read(path)`, `write(path, text)`.
5. Модель: `nodes_call("nbw", 4, "read", {path: "/etc/hostname"})` → текст.
6. Дальше вызовы идут без обзора: номер API, имя узла и метода уже в контексте.

Два лишних обращения в начале сессии — цена за то, что контекст не растёт от
числа узлов. Если API зовут постоянно, его можно «поднять» в нормальный
типизированный тул (см. §6).

### 5.2. Ошибки — часть интерфейса

Валидация двухуровневая, и оба уровня отвечают одинаково внятно.

**Сервер** проверяет `node`, `api`, `method` и `data` по схеме метода до
постановки в очередь:

```
bad args: state: expected one of [on, off], got "on1"
unknown method "bright" in api 2 (есть: set, get)
unknown node 42 (есть: 17 — nbw, 21 — desktop)
```

**Узел** может отказать сам — и это не дублирование, а разные причины. Главная:
два разных по сути API заанонсированы под одним id, справочник хранит схему
первого, а узел реализует второй. Тогда сервер пропустит вызов по своей схеме,
а узел ответит `{ok:false, code:'bad_request', message:'…'}`.

Такой отказ доходит до модели дословно, с указанием, кто именно его вернул:

```
17 — nbw: bad_request: no method set in api 2, есть: switch, state
```

Текст узла не переписывается и не глотается: модель видит ровно то, что
сказал исполнитель, плюс имя узла, чтобы не путать с ответом сервера. Скрывать
расхождения схем нельзя, блокировать из-за них вызовы — незачем.

### 5.3. Адресация: два номера

`call(17, 2, 'file-ls', {path: '/'}, 120)` — узел 17, API 2, метод, аргументы,
таймаут в секундах (не задан — берётся у узла, у узла не задан — 60). Ничего про права в сигнатуре нет: режим берётся из сессии
модели, а если его не хватило — обёртка спросит человека сама (§13.3).
В результате эхом идут `node`, `api` и `method` — чтобы промах двумя числами
был виден сразу, а не в чужом логе.

Оба номера автоинкрементные и не переиспользуются, поэтому «17» значит один и
тот же узел всегда — и в этой сессии, и в следующем году. Отдельного uuid нет.

Риск, который надо назвать: два числа рядом можно переставить местами, и
`call(2, 17, …)` уйдёт другому узлу. Проверка `api_no` по `node.apis`
отсекает большинство таких промахов (`unknown api`), но не все: если у обоих
узлов есть API с этим номером и в нём есть этот метод, вызов уйдёт не туда.
Поэтому:

- `nodes_list()` печатает **обе** стороны связки: `17 — nbw (apis: 2, 5)`.
  Модель видит, какой номер какой машине соответствует, и обычно копирует
  пару из этого вывода, а не сочиняет;
- ошибки называют обе стороны, а не только номер: `unknown node 42 (есть: 17
  — nbw, 21 — desktop)`, `unknown api 2 for node 17 — nbw (apis: 5, 9)`;
- если промах всё же случился и метод на чужом узле существует, спасения нет.
  Это цена дешёвой адресации, и она принята сознательно.

`node` принимает и алиас (`nbw`) — он разрешается в тот же номер. Стоит это
ничего, а промах «забыл номер» закрывает.

## 6. Позже: типизированные тулы и локальный узел

### 6.1. Типизированные тулы

Если какой-то API зовут часто, `dsh-nodes` может регистрировать его методы
как обычные тулы DSH — с настоящей JSON Schema, по одному на метод. Проверено,
что это возможно: `ToolDefinition.parameters` принимает сырую JSON Schema
(`dsh-mcp-client`, `lib/index.js:185`), а смена набора тулов на лету
предусмотрена ядром (источник сообщений `tool-registry` в `dsh-llm`).

Это не основа, а оптимизация: включается по списку API в конфиге, и по
умолчанию выключена, чтобы не вернуть ту самую проблему с контекстом.

### 6.2. Локальный узел: встроенные MCP как узел 1

Местные MCP-сервера профиля (`dsh-mcp-client`) — такие же API, как удалённые,
и их тоже можно показать через справочник: узел `1`, имя `local`, без токена,
а API — из уже зарегистрированных тулов `mcp__<server>__<tool>`. Тогда
`nodes_call(1, …)` работает там же, где `nodes_call(17, …)`, и у модели один
набор имён на местное и удалённое.

- `id = 1` резервируется: первая миграция вставляет строку
  `node(1, 'local', local=1)`, поэтому `AUTOINCREMENT` начинает выдавать с 2.
  Удалить её нельзя, токена у неё нет и быть не может.
- Справочник для узла 1 наполняется не через `/announce`, а из `ctx.tools`:
  `schemas(scope)` отдаёт по одной схеме на каждый видимый тул, `get(name)` —
  определение с `parameters`. Значит отобрать `mcp__<server>__<tool>` и
  разложить по API можно без хаков; это проверено по типам `dsh-tools`, а не
  предположено.
- Команды для узла 1 не идут в очередь: вызов исполняется в процессе и
  оборачивается в тот же `{status, message, results}`. Нужен гард: тулы
  `nodes_*` через локальный узел не зовутся — иначе рекурсия.
- Не на первом этапе: это удобство консистентности, а не работающий транспорт.

### 6.3. Привязка узлов к пользователям (не сейчас)

Позже узел будет принадлежать пользователю, а не «всем в этом DSH»: список
пользователей у нас уже есть — плагин `dsh-assistants` с его персонами и
привязкой к сессиям, его и используем.

Что это меняет — и почему откладывание бесплатно:

- владение это **серверная политика над реестром**: колонка `owner` в `node`,
  назначение в админке, фильтрация `nodes_list()`. Протокол узла о ней не
  знает и знать не должен, поэтому ни спека (§17), ни клиенты не меняются;
- меняется адресат аппрува (§13.3): сейчас спрашиваем того, кто в сессии, а
  правильно — владельца узла. Отсюда же вырастает «второй аппрув на узле»,
  который сегодня не делаем: это не отдельный человек на машине, а именно
  владелец устройства;
- проверка прав на вызов (`nodes_call` к чужому узлу) — тоже сюда.

Пока этого нет, узлы видны всем сессиям DSH, и это надо помнить, раздавая
токены.

## 7. Presence и keepalive

- WS: серверные `ping`/`pong` раз в 20 с; узел раз в 20–30 с шлёт
  `{"t":"alive","known":N,"epoch":…,"boot":…}` — заодно это и вопрос про state
  (§4.2), отдельного «я жив» нет.
- Три пропуска подряд или закрытый сокет → `offline`. Это **состояние в
  админке, а не класс ошибки**: висящие команды узла не раскручиваются.
  Переподключение штатное, узел в этот момент мог исполнять команду, и
  выбросить его работу из-за моргнувшей сети — худшее из решений.
- Судьба висящей команды решается её собственным `timeout`: переподключится
  без рестарта — либо выполнит, либо нет; не переподключится — сработает
  таймаут, и модель получит `timeout`, а не выдуманный `node offline`.
  Результат, пришедший после реконнекта, принимается (§4.4).
- **Новое соединение вытесняет старое.** Один узел — один сокет: новый
  `hello-ok` закрывает предыдущий кодом `4001` (`replaced`). Иначе `state`
  уезжает в мёртвый сокет, а `waiting` принадлежит неизвестно кому. После
  вытеснения `waiting` сбрасывается: ответ на «узел спрашивал» больше не нужен,
  он спросит заново.
- Presence в памяти: после рестарта все `offline`, пока не придут снова.
- Узел без WS может тянуть команды, но считается `offline`.

## 9. Авторизация

- Токен узла: 32 случайных байта, base64url; в сторе только `sha256`.
- Передача — `Authorization: Bearer <token>` на HTTP и на WS-upgrade. В URL
  токен не кладём: он течёт в логи nginx и в историю шелла.
- Сравнение — `crypto.timingSafeEqual` по дайджестам; `401` без подробностей.
- Перевыпуск: старая запись заменяется, WS узла закрывается кодом `4001`.
- Админ-токен отдельный: из конфига `adminToken`, иначе генерируется при
  старте в `$DSH_HOME/storages/dsh-nodes/admin.token` (0600) и один раз
  печатается в лог; страница хранит его в `localStorage`. Сознательный уход
  от правила «админ-API под owner-гейтом `/api`»: узлы заводятся и с чужой
  машины.
- Ограничение частоты: token bucket в памяти на «адрес+токен» (~20 rps,
  всплеск 40), `429` с `Retry-After`. Адрес — из `X-Real-IP`, но **только если
  соединение пришло с локального адреса** (то есть от nginx); снаружи заголовок
  игнорируется и берётся адрес сокета. `X-Forwarded-For` не парсим вовсе — он
  подделывается тривиально.

### 9.1. Первичная регистрация (self-enroll)

Два способа завести узел, и они не конфликтуют:

| способ | когда | кто делает |
|---|---|---|
| **pre-provision** | серверы, CI, скрипты | админ создаёт узел и отдаёт токен заранее |
| **self-enroll** | «поставил и забыл»: ноутбук, лампа, малинка | узел приходит сам, админ подтверждает |

Поток self-enroll:

```
1. клиент при первом запуске генерирует себе uuid и хранит его вечно
   (~/.dsh-nodes/id), печатает в консоль:  nbw / 7f3a-9c21
2. POST /v1/enroll {uuid, name: "nbw", proto, client_version}
   → 202, узел попадает в список unregistered
3. клиент опрашивает GET /v1/enroll/{uuid} раз в 5 с
4. человек открывает админку, видит «nbw · 7f3a-9c21 · 192.0.2.17 · 2 мин»
   и жмёт «допустить»
5. следующий опрос отдаёт {token, node, alias} — токен одноразово, в ответе
   только в этот момент
6. клиент сохраняет токен и работает обычным путём
```

Что здесь важно и почему:

- **uuid — не секрет.** Он печатается в консоль и уходит по сети открыто.
  Авторизацией он не является никогда: только метка, по которой человек
  находит строку в списке. Токен выдаётся один раз и живёт своей жизнью.
- **Одобрение — только человек в админке** (admin-токен), автоматики нет.
  Строка показывает имя, короткий uuid (8 символов), адрес и сколько висит.
- **`unregistered` имеет TTL** (`enrollTtlSeconds`, 900 с) и потолок списка
  (`maxPendingEnroll`, 50). Иначе публичный эндпоинт превращается в способ
  завалить админку мусором; при переполнении новые заявки получают
  `rate_limited`, а не вытесняют старые.
- **Токен передаётся ровно один раз.** Он держится в памяти сервера, в базе
  лежит только `sha256` после выдачи. Рестарт сервера в окне передачи (10 мин)
  означает «не успели» — заявка остаётся `approved`, но токен надо
  перевыпустить в админке обычной кнопкой. Хранить bearer-секрет в базе ради
  редкого случая не будем.
- **Имя не уникально у узла, уникален алиас.** Если «nbw» уже занят, сервер
  выдаст `nbw-2` и покажет его клиенту в ответе — пусть печатает то, что
  реально получилось.
- **Дефолты доступа — безопасные** (§11.3): `access = 'none'`,
  `allow_escalation = 1`. Одобрение не выдаёт прав; оно только заводит узел.
- Если админ удалит узел, тот же uuid снова попадёт в `unregistered` и
  потребует нового одобрения. Это правильно: удаление — это отзыв.

Хранение заявки: `enrollment(uuid PRIMARY KEY, name, client_version, proto,
ip, first_seen, last_seen, status, node, token_sha256_handed_at)`.

## 11. Модель данных

### 11.1 Что где живёт

Модель раздвоена намеренно: на диск — то, что должно пережить рестарт, в
память — то, что принадлежит текущей жизни процесса.

| объект | носитель | почему |
|---|---|---|
| узлы, алиасы, токены | БД | предмет администрирования |
| справочник API (`apidef`) | БД | контракты, из них строятся тулы |
| связи «узел держит API» | БД | many-to-many, `refcount` из них |
| `epoch` | БД | счётчик поколений сервера |
| аудит эскалаций | БД | «кто разрешил что и когда» — переживает всё |
| счётчик команд `state` | память | номер в пределах жизни сервера; поколение различает `epoch` |
| watermark `known` | память | сбрасывается на старте вместе с `state` |
| флаг `waiting` | память | привязан к живому сокету |
| очередь команд | память | ждущий — живой промис модели |
| промисы по `seq` | память | то же |
| отказы `denial_id` | память | живут минуты, между ними рестарт переживать нечем |
| presence, сокеты, счётчики за окно | память | по определению |

### 11.2 Схема

`$DSH_HOME/storages/dsh-nodes.sqlite`; `admin.token` — файл (0600).
`PRAGMA journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout=5000`.

```sql
CREATE TABLE meta (                  -- служебные пары; здесь живёт epoch
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);

CREATE TABLE node (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,  -- номер узла = адрес в вызовах
  local           INTEGER NOT NULL DEFAULT 0 CHECK (local IN (0,1)),  -- 1 = локальный узел (§6.2)
  name            TEXT NOT NULL,                      -- отображаемое имя; дублируется алиасом
  token_sha256    TEXT UNIQUE CHECK (token_sha256 IS NULL OR length(token_sha256) = 64),
                                                      -- NULL = токен отозван
  token_issued_at INTEGER,
  access          TEXT NOT NULL DEFAULT 'none'
                  CHECK (access IN ('read-only','workspace-write','danger-full-access','none')),
                                                      -- что узел ОБЯЗАН обеспечить (ставит админ)
                                                      -- по умолчанию «не умеет изолировать»
  workdir         TEXT,                               -- корень записи для workspace-write
  default_timeout INTEGER,                            -- секунды, NULL = конфиг плагина (60)
  allow_escalation INTEGER NOT NULL DEFAULT 1 CHECK (allow_escalation IN (0,1)),
  proto           INTEGER,                            -- версия протокола от узла; NULL = не объявлялся
  client_version  TEXT,                               -- «dsh-nodes/0.1.0»; только для глаз
  created_at      INTEGER NOT NULL,
  last_seen       INTEGER,
  last_null_at    INTEGER                             -- когда последний раз приходил known: null
);

CREATE TABLE node_alias (            -- все имена, которыми зовут узел
  alias TEXT PRIMARY KEY COLLATE NOCASE,
  node  INTEGER NOT NULL REFERENCES node(id) ON DELETE CASCADE
);
CREATE INDEX node_alias_node ON node_alias(node);

CREATE TABLE api (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,  -- api_no для модели
  key        TEXT NOT NULL UNIQUE,               -- sha256(name \0 version) | sha256(name \0 node:<id>)
  name       TEXT NOT NULL,                      -- свободный текст: «linux shell»
  version    TEXT,                               -- NULL = API личное для узла
  apidef     TEXT NOT NULL,                      -- JSON: описание + методы со схемами
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);

CREATE TABLE node_api (              -- кто какой API держит; второе зеркало отношения
  node INTEGER NOT NULL REFERENCES node(id) ON DELETE CASCADE,
  api  INTEGER NOT NULL REFERENCES api(id)  ON DELETE CASCADE,
  PRIMARY KEY (node, api)
);
CREATE INDEX node_api_api ON node_api(api);

CREATE TABLE enrollment (            -- заявки на регистрацию (§9.1)
  uuid         TEXT PRIMARY KEY,     -- его генерирует клиент и печатает человеку
  name         TEXT NOT NULL,        -- как клиент себя назвал
  client_version TEXT,
  proto        INTEGER,
  ip           TEXT,
  first_seen   INTEGER NOT NULL,
  last_seen    INTEGER NOT NULL,
  status       TEXT NOT NULL DEFAULT 'pending'
               CHECK (status IN ('pending','approved','rejected','expired')),
  node         INTEGER REFERENCES node(id) ON DELETE SET NULL,  -- появится после одобрения
  handed_at    INTEGER               -- когда токен отдали (plaintext не хранится)
);
CREATE INDEX enrollment_status ON enrollment(status, last_seen);

CREATE TABLE escalation (            -- аудит; намеренно БЕЗ внешних ключей
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  at          INTEGER NOT NULL,
  node        INTEGER NOT NULL,      -- номер узла на момент события
  node_name   TEXT NOT NULL,         -- снимок, чтобы запись читалась после удаления узла
  api         INTEGER NOT NULL,
  api_name    TEXT NOT NULL,
  method      TEXT NOT NULL,
  args_hash   TEXT NOT NULL,         -- sha256 канонического JSON аргументов
  requested   TEXT,                  -- какой режим просили
  granted     TEXT,                  -- что разрешил человек
  outcome     TEXT NOT NULL,         -- allowed-once | rejected | cancelled | unavailable
  requested_by TEXT NOT NULL         -- 'wrapper': эскалацию инициирует обёртка, не модель
);
CREATE INDEX escalation_at ON escalation(at);
```

`refcount` в схеме **отсутствует**: это `COUNT(*)` по `node_api`. Двух истин об
одном отношении не бывает, поэтому уборка записи `api` — не «уменьшить
счётчик», а «удалить записи, у которых не осталось связей».

### 11.3 Инварианты

- `node.name` при создании автоматически становится алиасом: имя, которым
  нельзя позвать, — ловушка. Дальше алиасов может быть много, все уникальны
  без учёта регистра.
- `token_sha256` уникален, при отзыве — `NULL`. Отозванный узел остаётся в
  базе: иначе пропадёт история и его `apis` начнут исчезать из справочника
  раньше, чем это заметит человек.
- `api.key` уникален: одно и то же `(name, version)` с разных узлов — одна
  запись. Без версии `key` включает номер узла, поэтому два безымянных
  `linux shell` не склеиваются.
- `api` без единой связи в `node_api` удаляется в той же транзакции, что и
  объявление. Отдельной «уборки по расписанию» нет.
- Узел с `local = 1` (id 1) вставляется в первой миграции и удалению не
  подлежит — это проверка в коде, не в SQL: триггеры ради одного случая
  дороже пользы.
- `escalation` не каскадится ни с чем: аудит должен пережить и узел, и API.
- `enrollment.uuid` — метка, а не узел: связь с `node` появляется только после
  одобрения (`node` = NULL до него). Просроченные `pending` чистятся на старте и
  раз в минуту: `status = 'expired'` сохраняется ради истории, но в списке
  заявок не показывается.
- `access`/`workdir`/`allow_escalation` — **администраторские**, они на диске.
  Узел в `/announce` объявляет, что физически умеет (`can`), но не решает за
  админа: эффективный режим — админский, а если узел не может его обеспечить,
  все confining-вызовы получают `sandbox_denied` (см. §13.2).
- Дефолты намеренно неудобные, а не удобные: новый узел приходит с
  `access = 'none'` и `allow_escalation = 1`. То есть «ничего не умеет, но
  спросить разрешено». Админ увидит в админке объявленное узлом `can:
  workspace-write (bwrap)` и включит его одним нажатием. Дефолт
  `danger-full-access` был бы тихим повышением прав — ровно тем, чего этот
  документ избегает.

### 11.4 Состояние в памяти

```
runtime = {
  epoch, boot,                       // epoch из meta, boot — uuid на этот старт
  nodes: Map<number, {
    state,       // последний выданный seq; 0 на старте
    served,      // watermark сервера: max выданного; 0 на старте (курсор узла живёт на узле)
    waiting,     // узел спросил и ждёт state
    online, socket, lastAlive,
    queue:   Command[],              // по возрастанию seq
    bySeq:   Map<number, Command>,
    waiting_promises: Map<number, { resolve, timer }>,
  }>,
  // denial_id сервер НЕ хранит: его выдаёт и проверяет узел, а обёртка держит
  // свой отказ в области видимости вызова, пока ждёт аппрува (§13.3)
  counters: { lateResults, escalations: {approved, rejected}, sandboxDenied }  // окно
}
```

`Command = { seq, node, api, method, args, timeoutSeconds, createdAt, expiresAt }`.
`fingerprint` — sha256 от `node/api/method/канонический args`, чтобы эскалация
не могла переехать на другую команду (§13.3).

На старте: `epoch += 1` в `meta`, `boot := randomUUID()`, всё остальное в
`runtime` — с нуля. База при этом не меняется: `node.state` и `node.known` в
ней нет намеренно — это состояние поколения, и `epoch` его и различает.

### 11.5 Транзакции и миграции

Объявление узла — **одна транзакция**: посчитать `key`, найти или вставить
`api`, снять `node_api` для пропавших, добавить для новых, удалить `api` без
связей. Уборка не может отстать от объявления, потому что это один `COMMIT`.

`PRAGMA user_version` — версия схемы; миграции по возрастанию на старте, каждая
в своей транзакции. Первая (`0 → 1`) создаёт всё выше и вставляет локальный
узел `1`.

Схема прогнана на этой машине (Node 24.22.0, `node:sqlite` 3.53.4): все шесть
таблиц создаются, `refcount` считается, `api` без связей удаляется, каскад
снимает алиасы вместе с узлом.

`AUTOINCREMENT` даёт гарантию, которую иначе пришлось бы держать счётчиком:
номер удалённой записи не переиспользуется (проверено на этой машине, Node
24.22.0, SQLite 3.53.4 — после `DELETE` номера идут `1, 3`). Старый `api_no`
из прошлой сессии не укажет на другой API.

### 11.6 Обслуживание

- Всё, что пишется, пишется либо в транзакции, либо не пишется вообще.
- Лог: постановка, выдача, результат, таймаут, `bad args`, `409`, удаление
  записи справочника, эскалации — в общий лог плагина.
- Бэкап: файл `*.sqlite` вместе с `-wal`/`-shm`, либо
  `PRAGMA wal_checkpoint(TRUNCATE)` перед копированием.

## 13. Права: режим доступа и песочница

### 13.1. Как это устроено в DSH (проверено по пакетам, не по памяти)

Режим — это `SandboxMode = 'read-only' | 'workspace-write' | 'danger-full-access'`.
Но запрет **не проверяется перед запуском**. `ctx.sandbox` — провайдер
изоляции, который *заворачивает argv*:

```
confine(policy) → { argv: [runner, профиль, --, …наша команда],
                    enforcement: 'full' | 'partial',
                    denialSignatures, runnerFailureRules }
```

Бэкенды — bwrap (read-only привязки дают `EROFS`), Landlock (`EACCES`),
Seatbelt (`EPERM`), Windows ACL. То есть «нельзя» произносит **ядро**, когда
команда пытается писать; исполнитель распознаёт диалект отказа своего бэкенда
и отличает «песочница не пустила» от «runner сломался, команда не запускалась».

Политика передаётся **на каждый вызов** (`mode` + `workspaceRoot` +
`sessionId`), а не фиксируется на провайдере. Режим сессии резолвит
`ctx.sandboxPolicy.resolve({session, mode?})`, дефолт в конфиге — `read-only`
как fail-safe; пресеты (`dsh-permission-presets`) связывают preset с парой
«режим песочницы + политика аппрувов»; расширение режима идёт через
escalation с подтверждением человеком.

### 13.2. Что переезжает на узел

Переезжает: контракт API (методы и аргументы) и **факт режима**. Не
переезжает: сама песочница — она про ядро и ФС той машины, где команда
исполняется.

У узла есть две вещи, которые задаются в админке (или приходят из его
собственного конфига):

| поле | смысл |
|---|---|
| `access` | режим по умолчанию: `read-only` / `workspace-write` / `danger-full-access` |
| `workdir` | корень, внутри которого разрешена запись |
| `allow_escalation` | готов ли узел вообще обсуждать обход (§13.3) |

Режим едет **в команде** — форма команды и результата описана один раз, в
§4.3 и §4.5; здесь только то, что относится к правам.

- сервер берёт `mode` и `root` из **сессии модели**: `ctx.sandboxPolicy.resolve()`
  — это ровно тот режим, в котором работал бы местный `bash`, иначе удалённый
  шелл оказался бы дырой в политике, которую видит пользователь;
- узел применяет своим раннером и возвращает в результате фактическое —
  `sandbox: {mode, enforcement, denied}` где `denied` это диалект отказа
  (`EROFS`/`EACCES`), тот же словарь, что у DSH;
- узел при `/announce` объявляет, что умеет:
  `{"access":"workspace-write","workdir":"/home/u","backend":"bwrap",
    "enforcement":"partial","allow_escalation":true}`.
  В `nodes_list` это видно модели у узла, а не у API: `21 — desktop (offline 3h, access: workspace-write)`;
- **два разных отказа**, и их нельзя смешивать:
  - `sandbox_denied` — узел не может обеспечить запрошенный режим или корень:
    у него `access = none`, запрошенный режим строже его `access`, или `root`
    вне `workdir`. Команда даже не запускалась;
  - `denied` — узел запустил в песочнице, а ядро отказало (`EROFS`/`EACCES`).
    Команда запускалась и упала на записи.
  Оба возвращаются с маркером и с шансом на эскалацию (§13.3);
- нет ничего опаснее тихого понижения: если узел не умеет запрошенный режим,
  он отказывает одним кодом `sandbox_denied` с причиной в тексте
  (`node cannot confine: access=none`), а не выполняет «как получится».

### 13.3. Эскалация: обёртка спрашивает сама

Модель ничего не просит и ни о чём не договаривается. Она зовёт узел; если
прав не хватило — спрашивает обёртка, по той же схеме, что локальный bash в
DSH:

```
1. модель → nodes_call(...)                       обычный вызов, режим из сессии
2. узел → sandbox_denied {denial_id, reason, requested, granted}
3. обёртка (наш код, не модель) держит отказ в памяти и вызывает
   ctx.approval.request({toolName:'nodes_call', callId, reason: <факты вызова>})
   → allowed-once | rejected | cancelled | unavailable
4. только allowed-once: тот же вызов уходит на узел НОВОЙ командой (новый seq)
   с флагом {"approved": {"denial_id": "...", "mode": "...", "once": true}}
5. узел сверяет denial_id (свой, живой, одноразовый) и исполняет без изоляции
6. модель получает ОДИН результат — тот, что вернул исполнитель
```

Что это даёт по сравнению с «модель сама просит `sandbox_permissions`»:

- модель не может ни инициировать, ни пропустить диалог: её ручки в этом нет
  вообще, аргументов для эскалации в схеме тула не существует;
- нет второго способа адресовать вызов: модель не может «попросить пошире»
  заранее, не получив отказа;
- `denial_id` теперь внутреннее дело узла и обёртки — модели он не передаётся,
  поэтому нечему путаться (§ ревью M3/M9 снимаются).

Правила, без которых это станет опасно:

- **одна эскалация на вызов.** Эскалировать эскалацию нельзя: если и после
  «да» узел отказал, это финальная ошибка, а не повод спросить ещё раз;
- **таймер команды стартует после ответа человека.** Иначе человек, думавший
  40 секунд над командой с `timeout: 20`, получит `timeout` вместо исполнения.
  Время на раздумья не входит в `timeout` вообще;
- **`cancelled` (отмена вызова) — в очередь ничего не уходит**: узел не должен
  узнать, что команда была;
- **показ человеку — факты, а не текст модели.** В `reason` идёт
  `17 — nbw, api 3 (linux shell), exec: rm -rf build, режим read-only →
  danger-full-access`. Модель этот текст не пишет и не может повлиять на него;
- **узел проверяет `denial_id`**: он свой, живой и одноразовый. Обход «на
  другой команде» невозможен, потому что `denial_id` привязан к отпечатку
  вызова (sha256 от `node/api/method/канонический args`).
- **узел может отказать и с валидным `approved`.** Локально в DSH разрешение
  человека означает «можно»: дальше решает только песочница. У узла ступеней
  на одну больше, и это надо понять буквально.

  Пример. Ты запустил узел на своём ноутбуке и забыл. Потом этим же DSH
  пользуется другой человек (общий аккаунт, другая сессия, субагент) — или
  просто модель ошиблась с аргументами. Человек в диалоге нажал «да» на
  команду `rm -rf ~/projects`. Значит ли это, что машина обязана выполнить?
  Нет: владелец ноутбука может держать у себя `allow_escalation: false` или
  свой список запретов. Тогда узел отвечает вторым отказом, и это не сбой, а
  его право.

  Что видит модель: обычную ошибку с текстом узла
  (`sandbox_denied: owner policy forbids escalation`). Спросить человека
  ещё раз нельзя — одна эскалация на вызов, иначе получается бесконечный
  диалог «ну пожалуйста».

  Обратная сторона, которую надо назвать: токен сервера **не** даёт права
  командовать машиной. Если бы давал, любой, кто получил доступ к DSH, получал
  бы root на всех подключённых узлах — а это ровно то, чего мы избегаем.
  Второго аппрува на стороне узла пока нет: это тот же владелец машины, а
  владение узлами появится вместе с привязкой к пользователям (§6.3).

Ожидание ответа ограничено: `approvalTimeoutSeconds` (по умолчанию 300 с, пять
минут). Молчание дольше — это `unavailable`, то есть отказ; бесконечное
ожидание в headless-сессии означало бы повисший ход.

Что получает модель во всех неразрешившихся случаях — один код:

| исход аппрува | модель |
|---|---|
| `rejected` | `{status:'error', code:'escalation_rejected', message:'rejected by user'}` |
| `cancelled` | `{status:'error', code:'cancelled', message:'cancelled'}` |
| истекли 300 с | `{status:'error', code:'escalation_rejected', message:'approval timeout'}` |
| `unavailable` (headless) | `{status:'error', code:'escalation_rejected', message:'no approval channel'}` |

Тайминги не складываются: `timeout` команды считается **только** от постановки
в очередь, ожидание человека в него не входит. Поэтому худший случай одного
вызова — `approvalTimeoutSeconds + timeout` (300 + 60 по умолчанию), и это надо
знать, читая §5.

Отказы человека: `rejected` и `cancelled` → модель получает
`{status:'error', message:'sandbox_denied: escalation rejected by user'}`.
`unavailable` (нет канала аппрува, headless) — тот же отказ.

Переключатель: `autoEscalate` (по умолчанию `true`). Выключили — отказ уходит
модели как есть, без диалога; это режим «спрашивать не у кого».

Что узел **не** может проверить: действительно ли человек нажал «да». Это
доверие к серверу, у которого есть токен узла. Факт эскалации виден в аудите
(§11.2) и в админке.

## 14. Модель угроз

- Без токена доступны только статика админки и `401`.
- Токен узла = право объявлять API, читать команды и подсовывать результаты.
  Лечится перевыпуском, отзыв закрывает соединение.
- `shell`/`fs` по сети — тот же класс риска, что `bash` на хосте. Позиция
  проекта: **что узел объявил, то модель и может**; белых списков методов нет,
  ответственность за метод — на том, кто его реализовал. Это пишется в README.
- Узел может объявить чужой `api` и врать в результатах. Защиты от этого нет
  и не планируется: узлы принадлежат тому, кто их поставил.

## 17. Машинопроверяемая спека

Клиентов будут писать на разных языках, поэтому протокол живёт в файлах, а не
в этом тексте. Текст объясняет *почему*, файлы описывают *что*.

```
spec/
  nodes.openapi.yaml     # OpenAPI 3.1: HTTP-маршруты, токены, коды ответов
  frames.schema.json     # JSON Schema 2020-12: кадры WS, tagged union по полю t
  errors.schema.json     # закрытый словарь кодов ошибок
  tools.schema.json      # схемы четырёх тулов модели (ctx.tools ждёт JSON Schema)
```

Правила:

- **Одна истина.** Рантайм валидирует входящее **по этим же файлам** (`ajv`,
  draft 2020-12), а не ручными проверками: спека и код не могут разойтись,
  потому что код читает спеку. Кадры, которые сервер шлёт, тоже проверяются
  в тестах — клиент не должен получать то, чего нет в контракте.
- Клиенты генерируются: `openapi-generator -i spec/nodes.openapi.yaml -g go`
  (ts, python, csharp — что угодно). Руками пишется только то, чего в OpenAPI
  нет: цикл узла (§4.3) и семантика.
- `proto: 1` в `/announce` — версия спеки. Несовпадение не блокирует (§3), но
  в админке видно.
- `args`/`data` вызова **не** описываются в спеке: их схема приходит из
  справочника API. Поэтому `nodes_call` объявляет `data: object` и валидирует
  внутри по `apidef`.
- WebSocket в OpenAPI не входит, поэтому кадры — отдельная JSON Schema
  (tagged union по `t`); рантайм и тесты берут один и тот же файл.

Закрытый словарь ошибок (`errors.schema.json`), чтобы клиенты умели
реагировать, а не разбирать текст:

| код | когда |
|---|---|
| `unauthorized` | нет/плохой/отозванный токен (`401`) |
| `rate_limited` | сработал bucket (`429`) |
| `bad_request` | тело не по схеме, неизвестные поля (`400`) |
| `proto_garbage` | кадр не разбирается — закрытие `4400` |
| `unknown_node` / `unknown_api` / `unknown_method` | адресация не сошлась |
| `bad_args` | аргументы не прошли схему метода |
| `args_too_large` / `result_too_large` / `body_too_large` | превышены `maxArgsBytes` / `maxResultBytes` / `maxBodyBytes` |
| `queue_full` | очередь узла на потолке |
| `timeout` | истёк `timeout` вызова |
| `cancelled` | вызов отменён, команда снята |
| `node_restarted` | узел пришёл с `known: null`, команда была выдана |
| `sandbox_denied` | узел не может обеспечить режим или ядро отказало |
| `escalation_rejected` | человек отказал, ожидание истекло или канала нет |
| `internal` | наш баг; текст только в лог, клиенту — код |

Что это даёт на практике: новый клиент начинается с генератора, а не с чтения
этого файла; расхождение клиента и сервера ловится валидатором на границе, а не
в проде через неделю.

Зависимость рантайма: `ajv` (+ `ajv-formats` при нужде). Всё остальное —
`node:http`, `node:sqlite`, `ws` — и так в ядре или в профиле.

## Песочница: что решает `ask`, а что потолок

Короткое правило, которое стоит держать в голове при настройке узла:

> `ask` решает, можно ли превратить отказ песочницы в вопрос человеку. Вопрос
> возможен только если потолок узла (`policy[url].max`) **шире** фактического
> режима команды. Если команда уже идёт на потолке, повышать некуда — отказ
> окончательный, и `ask` ни на что не влияет.

Примеры:

| потолок узла | пресет сессии | фактический режим | что будет при отказе |
|---|---|---|---|
| `rw` | `full` | `rw` (урезан потолком) | отказ, вопроса нет: повышать некуда |
| `full` | `read-only` | `ro` | вопрос «разрешить rw?», затем повтор |
| `full` | `full` | `full` | песочницы нет, отказа быть не может |

Модель может попросить режим уже разрешённого аргументом `sandbox` у
`nodes_call` (`ro` / `rw` / `full`) — это единственный способ получить зазор до
потолка при пресете `full`.
